## 0. 一句话

**目标是几格，一步是一格，你的能力是一格能做出多少。** 三句话都用同一个单位，拆解、排任务、看成长才能对得上账。

---

## 1. 单位：格

### 1.1 定义

**1 格 = 一个专注单元（默认 25 分钟）+ 一个可自检的产物。**

两个条件必须同时满足：

- **时间**：25 分钟（可配 30，对齐 42 期的半小时格）
- **产物**：这一格做完，能拿出一件东西，并且能自己判断成没成

只有时间没有产物，不算一格（看了一小时视频，零格）；只有产物没花时间，也不算（本来就会的东西，不算学习）。

### 1.2 为什么叫「格」

1. **一个词同时占两层**——「一格时间」和「一格产出」，不用再区分时间单位和产出单位；
2. **不另造新词**——42 期的原话就是「半小时一格」「把表填满」，产品语汇能直接接回视频，用户不用重新学；
3. **自带延伸词**，这套词能直接描述状态和进度：

| 词 | 含义 |
|---|---|
| **满格** | 这一格的产物做出来了 |
| **空格** | 这一格时间过了，但没留下产物（41 期说「整张表填满才有成就感」，空格就是那个洞） |
| **半格** | 做了一半，产物不完整 |
| **连格** | 连续几格都满——41 期说的「连续成功」，是产生动力的主要来源 |
| **断格** | 连格断了。不是为了惩罚，是为了让「断」这件事看得见 |

### 1.3 产出格分档（初始默认，待校准）

| 信息类型 | 1 格产出 = | 例子 |
|---|---|---|
| **过程** | 1 个跑通的小改动，或 1 个 bug 修完 | 接口能返回 hello |
| **抽象** | 1 个概念，不看资料能讲清 + 1 个例子 | 讲清 IoC 是什么、为什么用它 |
| **随意** | 20–30 个词条到能默写 | 20 个注解名 |
| **观点** | 1 个结论 + 2 条依据 | 选 JPA 还是 MyBatis，为什么 |

**为什么必须分类**：25 分钟背单词和 25 分钟调 bug，产出差十倍。只按时间量，等于用体温计量身高。

### 1.4 校准：从记录卡长出来

`~/.dsh/guide-tutor/` 的记录卡里每一段都是 20–50 分钟，天然就是「格」。缺的只有一列：**这一段做成了什么**。

做法：

1. 只对**挂了 `stepId` 的段**要求写一句产出，其他段不写（控制负担）；
2. 攒两周，算平均：过程类一段平均做成 0.8 个小改动 → 系数 0.8；
3. 系数写进 `user-skill.json`，拆解时用**用户的真实速率**估，而不是用默认值。

**没有这一步，这套东西就是拍脑袋。**

## 2. 拆解：按「可自检的产物」切，不按时间切

### 2.1 一步的公式

> **一步 = 一个可自检的产物 + 一次专注能完成 + 产物是下一步的输入**

### 2.2 三个校准器（同时满足才算一步）

| 校准器 | 合格线 | 不合格 |
|---|---|---|
| 时长 | 25–50 分钟 | 10 分钟就完了 → 太细；半天做不完 → 太粗 |
| 可自检 | 做完能自己判断成败，不用找人验收 | 「看了一章书」永远说得出「看了」 |
| 产物 | 做完能拿出一件东西 | 什么都没留下 = 没学 |

### 2.3 「太简单」和「太粗」的硬判据

| | 症状 | 修法 |
|---|---|---|
| **太简单** | 做完没有产物；产物不能给下一步用；不需要动脑 | 不看教程重做一遍；加一个边界条件；讲给别人听 |
| **太粗** | 说不出「做完什么样」；无法判断成败；**一句话里有两个动词** | 继续拆，拆到能写出产物名词为止 |

一句话检测法：**这句话里是不是有两个动词**。「学 Spring Boot 并写个接口」→ 两个，拆。「打开 IDE」→ 一个动词但没产物，太细。

「不能太简单」的真正判据：**做完之后，你能不能用一句话说出「我因此会了什么」？** 说不出，这一步对能力没有改变。

### 2.4 倒推拆解法（比正向切可靠）

正向切容易漏、容易切错地方。倒推：

1. **写验收句**——终点长什么样，必须可观察。
   不是「学会 Spring Boot」，而是「不看教程写出带增删改查的接口，curl 能通」。
2. **问上一环**：要做出它，必须已经有什么？
3. **递归**到「今天就能动手」的那一环。
4. **每一环写产物**（名词，不是动词）。
5. **正向走一遍**，检查有没有断点。

例（Spring Boot）：

```
验收：curl 能增删改查
 └ 接口能跑起来
    └ 能连上数据库
       └ 知道 datasource 怎么配
          └ 跑通过官方 quickstart  ← 今天的这一格
```

### 2.5 关键规则：拆不动 = 缺知识

如果某一步拆不出产物，或者拆不出下一步——停，把它换成「**搞懂 X**」，并按第 4 期的信息类型选学法：

| 类型 | 学法 |
|---|---|
| 抽象信息（IoC、AOP） | 先跑最小 demo，再回来看定义 |
| 过程信息（报错排查、配置） | 跟做一遍，别只看 |
| 随意信息（语法、注解名） | 查表用，别背 |

**这条规则最重要**：多数人卡住不是不够努力，是上一环的知识没补上。

### 2.6 两条约束

- **一次只推 1–2 个目标**。3 个并行必然都是半途（27 期「分动力」的直接推论）。
- **没有代价的步骤删掉**。每步挂一句「不做会怎样」，写不出来说明不重要。

## 3. AI 匹配：把单向标尺变成双向刻度

### 3.1 三个方向

| 方向 | 内容 | 由谁给 |
|---|---|---|
| **任务侧** | 难度：这件事要几格 | AI 出草案 + 用历史校准 |
| **用户侧** | 能力：一格能产出多少 | 从任务结果反推 |
| **匹配** | 成功率：这个任务做成的大概概率 | 前两者算出 |

### 3.2 派任务准则：成功率 70–85%

| 预估成功率 | 判断 | 动作 |
|---|---|---|
| **< 60%** | 太难 | 拆小，或补前置知识 |
| **60–85%** | 合适 | 派 |
| **> 85%** | 太易 | 加难度：删提示、加边界、要求不看资料 |

这条就是「太简单也不行」的量化版。

### 3.3 能力更新

每次完成记录三样：`difficulty`（预估几格）、`actualUnits`（实际几格）、`outcome`（done / partial / stuck）。

```
c_new = 0.7 × c_old + 0.3 × (difficulty / actualUnits × c_old)
```

指数滑动平均，限幅 ±15%，防止单次异常带偏。

三条判决：

- **连续 3 次 stuck** → 不是能力问题，是**缺前置知识**，自动触发倒推拆解；
- 实际 ≪ 预估且 done → 上调，该加难度；
- 预估 ≪ 实际 → 下调，估时一直偏乐观。

### 3.4 数据结构

`~/.dsh/guide-tutor/user-skill.json`：

```json
{
  "updatedAt": "2026-11-15T12:40:00+08:00",
  "units": {
    "过程": { "perUnit": 0.8, "samples": 23, "updatedAt": "..." },
    "抽象": { "perUnit": 1.2, "samples": 9 },
    "随意": { "perUnit": 25, "unitName": "词条", "samples": 6 },
    "观点": { "perUnit": 1.0, "samples": 3 }
  },
  "dailyCapacity": { "units": 2.4, "samples": 14 },
  "confidence": "low"
}
```

`confidence`：< 5 low、5–20 medium、> 20 high。low 时派任务保守，宁可给简单也不给卡死。

`goals.json` 的 step 结构：

```json
{ "id": "s1", "text": "跑通官方 quickstart，看到 hello",
  "estUnits": 1, "type": "过程", "check": "浏览器打开能看见 hello",
  "difficulty": 1, "actualUnits": null, "outcome": null,
  "dependsOn": [], "status": "doing" }
```

### 3.5 冷启动：三道探针

数据为零时不等两周，直接出三道探针，各 1 格：

| 探针 | 任务 | 测出 |
|---|---|---|
| 过程 | 给现有函数加一个参数校验 | 一格能改多少代码 |
| 抽象 | 讲清一个概念 + 举一个例子 | 一格能消化几个概念 |
| 随意 | 20 个词条默写 | 一格能记多少条 |

### 3.6 三个风险

1. **自评偏差**：自己标难度一定偏。所以难度「AI 出草案 + 历史校准」，**不让用户自报**。
2. **单位漂移**：能力涨了，三个月前标的难度就失真。解法：固定一组**参照任务**（同一批 benchmark，每 4 周重做），用它们的耗时漂移校正整个刻度。
3. **小样本不稳**：前 5 个任务基本不可信，界面上不能让低置信度的数字看起来和确定数字一样可靠。
