# 屏幕教学助手（guide-tutor / guide-coach）架构说明

> 写给外部分析者。目的是让你在不看代码的情况下，理解这套东西**是什么、怎么跑、数据长什么样、哪里最容易坏**。
> 写于 2026-11-24。版本：tutor `0.22.37`，coach `0.1.0`。

---

## 1. 一句话

两个跑在 **DeepSeek Harness（DSH）** 宿主里的本地插件，组成一个「个人学习操作系统」：

- **guide-tutor**：看得见屏幕，会在屏幕上画圈、写步骤、说话，教你操作；同时管**目标、清单、格数派发**。
- **guide-coach**：每 3 秒记录你在哪个窗口待了多久，和清单对账，出「今日记录」卡片；还会每 5 分钟让视觉模型看一眼屏幕，给这段时间打一句标签。

用户是一名学生，两个插件都只给他一个人用。没有多用户、没有账号、没有云端后端。

## 3. 进程模型与通信约定

这是整套东西最核心、也最容易误解的一点：**没有 RPC，没有 WebSocket**。

### 3.1 下行（宿主 → 浮层）：写文件 + 轮询

`state.json` 是唯一真相。宿主任何界面动作都是「改 state 再写盘」，浮层每 250ms 读一次、比较 mtime、变了就重建 UI。

```jsonc
{
  "panel":  { "visible": true, "mode": "panel|ball", "title": "…", "text": "…", "steps": [], "stepIndex": 0, "opacity": 0.9 },
  "annots": [ { "kind": "rect|circle|arrow|text|spotlight", "x": 0, "y": 0, "w": 0, "h": 0, "label": "…" } ],
  "card":   { "visible": true, "mode": "plan|record|goals|history", … },
  "chores": { "date": "2026-11-24", "items": [], "total": 2, "done": 0 },
  "dispatchUnits": 8,
  "recordViewDate": "2026-11-15"
}
```

### 3.2 上行（浮层 → 宿主）：追加 jsonl

用户点悬浮层上的任何东西（下一步、勾选、删除、派发、拖动结束），浮层往 `events.jsonl` 追加一行，宿主 tail 读：

```jsonc
{"type":"step"}                    // 点「下一步」
{"type":"chore_done","id":"c1"}    // 勾杂务
{"type":"plan_step","stepId":"g4-m1-s1"}  // 排下一步
{"type":"dispatch_goals","units":8}
{"type":"goal_removed","goalId":"g3"}
```

**为什么这么设计**：WPF 进程和 Node 进程之间没有现成的 IPC，而两者都要长期驻留。文件 + 轮询是最不容易死锁的方案，代价是 250ms 延迟和两类 bug——**写盘竞态**（两边同时写 state）和**事件重放**（tail 位置出错会重复处理）。

## 7. 核心数据模型

### 7.1 `goals.json`（tutor）—— 目标树

```jsonc
{
  "updatedAt": "2026-11-24T…",
  "goals": [{
    "id": "g4",
    "text": "学习日语到 N1",
    "acceptance": "N1 模拟真题正确率稳定在 60% 以上，且能不看字幕听懂一段 NHK 新闻并说出要点",
    "status": "active",              // active | done | paused
    "createdAt": "…",
    "milestones": [{                  // 阶段，3–5 个
      "id": "m1",
      "title": "N5 入门：把初级上啃下来",
      "steps": [{                     // 步骤，可以无限嵌套 children
        "stepId": "g4-m1-s1",         // 身份证，永不改
        "title": "学完第1课",
        "product": "一课笔记",         // 可自检的产物（名词）
        "check": "能读课文并说出语法点", // 怎么验
        "kind": "read",               // read|demo|fix|drill|feature|design
        "units": 1.5,                 // 约几格（1 格 ≈ 25–30 分钟）
        "status": "todo",             // todo|doing|done|dropped
        "dependsOn": [],              // 依赖的 stepId
        "caps": [{ "ref": "kana", "state": "have" }],  // 前置能力牌
        "children": []                // 子步骤，同结构，无限层
      }]
    }]
  }]
}
```

**关键规则**（`lib/decompose.js`）：

- **组步 vs 实步**：有 `children` 的叫组步，不派发、不计数；进度、格数、成功率只算叶子。
- **级联**：勾组步 = 勾所有后代；子步全 done → 祖先自动 done；子步撤销 → 祖先退回 todo。
- **硬上限**：`MAX_DEPTH = 8`、`MAX_MILESTONES = 6`、`MAX_STEPS_PER_MILESTONE = 8`、`MAX_UNITS = 3`（单步超过 3 格要求继续拆）。
- **校验**（`validateGoal`）返回问题码：`goal-text` / `no-acceptance` / `no-milestone` / `step-product` / `step-check` / `step-too-big` / `dep-missing` / `dep-cycle` / `too-deep`。**验收句只校验非空，不做语义判断**（用户明确要求：「掌握不掌握只要用户自己肯定就行」）。

### 7.2 `units.js` + `capabilities.js` —— 成功率模型

派发哪一步，不按顺序，按「**这个人现在做成的概率**」：

```
p = p_cap × p_skill × p_scale × p_novelty

p_cap     = ∏ 每张前置能力牌的满足度
            have 1.0 / partial 0.5 / lack 0 / unknown 0.75
            任一 lack → 0；≥2 个 unknown 再乘 0.9^(n-1)；无 lack 时下限 0.2
            全部 unknown 时整体按 0.9（不算逐张折价）
p_skill   = (该产物类型 done 次数 + 2) / (总次数 + 3)     Beta(2,1) 平滑
            无任何样本 → 冷启动先验 0.85
p_scale   = exp(−0.15 × (格数 − 1))
p_novelty = 见过很多 1.0 / 见过一些 0.93 / 陌生 0.85 / 完全未知 0.8

判定：p < 0.55 太难｜0.55–0.85 派｜> 0.85 太易
```

界面上**只显示成功率百分比**，不显示难度分。这套只管「做得出」，不管「愿不愿意做」。

### 7.3 `plan.json`（两份，语义不同）

tutor 的 `plan.json` 是**真清单**；coach 的 `plan.json` 通常为空，它读 tutor 的。

```jsonc
{ "date": "2026-11-24", "items": [{
  "id": "tmwhp0n2m", "from": "19:40", "to": "20:10",
  "title": "学新标日第2课语法", "place": "宿舍", "priority": "P1",
  "done": false, "doneAt": null,
  "goalId": "g4", "milestoneId": "m1", "stepId": "g4-m1-s2",
  "choreId": null,
  "auto": true,          // 由派发自动生成（可被 clearAutoSteps 撤回）
  "repeat": "", "note": "验：…"
}]}
```

`auto` 字段是 2026-11-16 加的，用来区分「系统排的」和「人手动排的」——派发重排时只撤 `auto` 的。

### 7.4 `chores.json`（tutor）—— 杂务

```jsonc
{ "updatedAt": "…", "chores": [
  { "id": "c1", "title": "洗衣服", "minutes": 30, "window": "evening", "every": "every2", "lastDone": "2026-11-17", "skip": [] }
]}
```

- `window`：`morning|noon|afternoon|evening|any` → 对应时段范围
- `every`：`daily|weekdays|weekly|every2|every3`
- `dueToday()` 按 `lastDone` 和 `every` 算今天该不该做
- 自动排程：每天 07:30 后第一次 tick，把这些事塞进清单空档（短的先排，间隔 5 分钟）

### 7.5 记录相关（coach）

| 文件 | 内容 |
|---|---|
| `activity-YYYY-MM-DD.jsonl` | 每 3 秒一行：`{t, proc, title(SHA256前12), full(是否全屏), idle(秒)}` |
| `labels-YYYY-MM-DD.jsonl` | 每 5 分钟一行：`{t, category, detail, shot, ms, idle, source}` |
| `state.json` 的 `record` | 记录卡片的渲染数据：段、汇总、清单对账 |

**「对上」三态**（`lib/activity.js`）：某段时间和清单条目重叠时——

- `对上`：有证据（进程名关键词出现在清单标题里，或 5 分钟内标签与标题有 ≥2 字公共子串）
- `清单内·别的`：在清单时段里，但干的是别的事
- `空窗`：不在任何清单时段

另外 `空闲`：键鼠 `idle ≥ 300` 秒超过一定跨度，单独切段（全屏播放器白名单除外）。

### 7.6 `settings.json` / `user-skill.json`

```jsonc
// settings.json（tutor）
{ "ttsEngine": "edge", "planReminders": false }   // planReminders=false 关掉全部清单提醒
```

```jsonc
// user-skill.json（tutor）
{ "kinds": { "read": {"done": 4, "total": 5}, "drill": {...} },
  "caps": { "java-basic": {"state": "have", "at": "…"} },
  "estimateBias": 1.1, "domains": {...} }
```

## 8. 一次典型调用链（「派发今天做什么」）

```
用户点「派发」→ 选 8 格
  ↓ (events.jsonl)
index.js dispatch_goals
  ↓ 写 settings.dispatchUnits = 8
  ↓ clearAutoSteps()  撤掉今天所有 auto:true 且未完成的条目
  ↓ goalCapacity()    算今天剩余空档 → 目标格数
  ↓ pickNextSteps(goals, {limit, maxUnits})
       每个叶子算 estimateWin → 过滤 p<0.55（太难）→ 按 p 降序取前 N
  ↓ nextFreeSlot()    绕开已有条目和杂务
  ↓ planRun add       逐条写入 plan.json（auto:true, stepId, note=验：…）
  ↓ pushState → 浮层重建清单卡片
```

反向：用户勾一条带 `stepId` 的清单条目 → `setPlanItemDone` → `onStepDone` → `goals.setStepStatus`（级联 + 祖先同步）→ `skill.record`（更新成功率和能力牌）→ `appendDaylog` → `pushState`。

## 9. 技术约束（踩过的坑，改代码前必读）

| 约束 | 原因 |
|---|---|
| **`overlay.ps1` 必须保留 UTF-8 BOM** | PowerShell 5.1 无 BOM 时按 GBK 读中文，直接语法报错。edit 工具会吃掉 BOM，每次改完要检查前 3 字节是否 `239,187,191` |
| **改 `index.js` / `lib/*.js` 要重启 DSH** | 只有 `overlay.ps1` 是独立进程能热重载；JS 部分在宿主进程里 |
| **`state.json` 会盖住代码里的默认值** | 改 `DEFAULT_STATE` 还要同步改盘上的 state.json |
| **WPF 里 TextBlock 挂鼠标事件不稳** | 必须外层套 `Border + Background=Transparent` 才能稳定命中 |
| **拖拽要用屏幕坐标 + DPI 换算** | `Window.Left/Top` 是 DIP，`PointToScreen` 是物理像素；150% 缩放时直接用会让窗口跑 1.5 倍 |
| **UIA 点不动 WPF 的 CheckBox** | 自动化测试得用真实鼠标事件（`SetCursorPos` + `mouse_event`） |
| **`guide_screen` 截不到悬浮层** | 截屏前会临时隐藏自己，验证浮层要用普通截屏 |
| **模板字符串里 `\/` 会被吞** | 正则要写成 `[/]` |
| **两个浮层不能重叠** | 都是 `AllowsTransparency + Topmost`，贴着会闪 |
| **PowerShell 脚本必须存 BOM** | 自己写的测试脚本同理，否则中文乱码 |

## 10. 已知问题与技术债

1. **`index.js` 4250 行、`overlay.ps1` 6643 行**，都是单文件巨兽。计划过拆成 4 个文件，没做。
2. **`plan.js` / `camera.js` / `edict.js` / `focus.js` 在两个仓库里重复**，已经分叉。
3. **两个插件都能管清单**，tools 名字撞车（`guide_plan`、`guide_focus` 两边都有），靠 DSH 的注册顺序决定谁生效。
4. **没有热重载的 JS 部分**，改完必须重启宿主，开发体验差。
5. **记录卡的空闲判定是启发式**：全屏播放器白名单硬编码（potplayer/vlc/mpc/mpv），浏览器全屏看视频会被判成空闲。
6. **成功率模型的先验是手调的**（0.85 / 0.9 / 0.8），没有真实数据校准；`estimateBias` 只是 EMA 兜底。
7. **`auto` 字段是补丁式修复**：之前派发会把用户手动排的条目一起撤掉，才加的标记。
8. **数据目录里同时有 tutor 和 coach 的 daylog**，历史文件重复，来源不清。
9. **`plan-history.json` 的部分日期是空的**（11-14/11-15），因为当时 coach 没拿到 tutor 的清单快照。
